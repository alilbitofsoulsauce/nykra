# Multi-file transactional Git patch engine

Nykra can evaluate and conditionally promote an **explicitly allowlisted multi-file Git patch** without allowing a failed patch or failed test to modify the original repository. ChatGPT with Rel.AI or any other agent can supply the unified diff; no Codex model is required.

## Behavior

The engine supports additions, modifications and deletions of at most **16 allowlisted regular text files**, with a maximum **128 KiB** patch and **2 MiB** per resulting file. It rejects path traversal, absolute paths, Git internals, symlinks, Windows device names, renamed/copied files, binary patches and permission changes.

It requires a clean, committed Git repository and records its precise HEAD. It clones the committed tree into disposable storage, checks and applies the Git diff, verifies changed-file SHA-256 hashes and executes unittest on that disposable checkout.

**Default executor:** explicitly pinned Docker image SHA-256, with no network, read-only root, nonroot user, dropped capabilities and resource limits. Its only code bind mount is the disposable checkout (read-only). Docker is not a certified malicious-code sandbox.

**Optional trusted test executor:** --trusted-local-tests runs repository Python tests directly on the workstation. Use only for code you already trust, never unknown contributions.

A preview or failed test leaves the original untouched. With explicit --promote and --approve, Nykra checks HEAD and clean status again under a repository advisory lock, then installs precisely the tested bytes via per-file atomic replacements. If promotion fails it restores original contents and modes. This provides rollback, but is not an ACID multi-file transaction visible atomically to all other processes.

Nothing commits, pushes, deploys or changes remotes automatically.

## CLI

Preview with a pinned Docker image:

~~~bash
python -m nykra patch-transaction --repository /path/to/repo \
  --patch-file proposal.diff \
  --allow engine/calc.py --allow engine/routes.py \
  --docker-image-id sha256:YOUR_64_HEX_IMAGE_ID --approve
~~~

For final promotion after reviewing a passing preview, add --promote to the same command. For a trusted local-only synthetic example, use --trusted-local-tests in place of --docker-image-id.

The default test command in the disposable checkout is Python unittest discover, or use --test-target tests.test_invoices for one explicit module.

For integration by other agents, import nykra.transactional_patch.run_transaction and supply a patch string, repository root, file allowlist, pinned image/test command and explicit approval.

## Hard engineering test

The historical single-function evaluator could not repair interacting multi-file defects as one patch. A fresh seeded Git fixture instead requires coordinating **two source files**: repairing an arithmetic total and removing an incorrect invoice URL offset. Both edits are necessary to pass independent tests; either alone fails.

The actual [offline pinned Docker engineering trial](evidence/v25_multifile_docker_trial.json) verified a two-file patch, exit code 0, passing tests and **10.361 seconds** recorded elapsed time. The fixture is synthetic, not an unseen real upstream bug, and the patch is constructed by the test harness rather than generated by a model.

The test module (tests/test_transactional_patch.py) exercises successful two-file repair, failure with one file omitted, clean/untracked protection, wrong allowlists, malicious paths, symlinks, copy/rename/mode rejection, patch corruption, real CLI preview/promotion, file creation, failing deletion, and simulated promotion rollback.

## Scope and limitations

- Strict textual Git patch subset: no binary assets, symlink changes, complex filenames or rename/copy operations.
- Clean committed checkouts are required for promotion. Staged/unstaged/untracked work prevents accidental overwrite.
- The Nykra lock only coordinates Nykra actions; outside processes are not automatically blocked. Rollback is best effort if machine or filesystem fails catastrophically.
- Running tests can execute arbitrary code. Docker confinement is risk mitigation, not absolute isolation; trusted local mode is **not isolated**.
- This establishes **multi-file workflow correctness under the tested conditions**, not increased coding-model accuracy or guaranteed agent productivity.
- The original multi-file module is source-tree functionality of the next release; no published binary or production permission manager is implied.
